# Z-Model 建模系统改进计划

## 一、竞品分析总结

### 1.1 对比对象

选取当前业界主流的建模/代码生成平台作为对比基准：

| 平台 | 类型 | 定位 |
|------|------|------|
| **ContextMapper** | DDD建模工具 | 基于DSL的战略DDD建模（限界上下文、上下文映射） |
| **JHipster/JDL Studio** | 代码生成平台 | 全栈代码生成，支持可视化建模和JDL DSL |
| **SketchDDD** | DDD建模工具 | 现代化可视化DDD建模，支持拖拽和DSL双模式 |
| **cp-ddd-framework (DDDplus)** | DDD框架 | 正向/逆向业务建模，轻量级DDD框架 |
| **Enterprise Architect / StarUML** | UML建模工具 | 全功能UML建模，支持代码生成和逆向工程 |
| **ERDPlus / dbdiagram.io** | 数据库建模 | ER图生成，DDL脚本输出 |
| **OneCodeDSM** | 低代码DDD建模 | 多种建模模式（Code First/View First/Model First） |

### 1.2 功能对比矩阵

| 能力维度 | Z-Model现状 | ContextMapper | JHipster/JDL | SketchDDD | cp-ddd |
|---------|------------|---------------|-------------|-----------|--------|
| **可视化建模** | ❌ 仅表单CRUD | ✅ 图形上下文映射 | ✅ UML类图可视化 | ✅ 拖拽+DSL | ❌ 代码标注 |
| **代码生成** | ❌ 无 | ✅ Spring Boot微服务 | ✅ 全栈生成 | ❌ | ✅ 正向生成 |
| **DDD核心概念** | ❌ 无（仅模型/属性/方法） | ✅ 限界上下文/聚合/实体 | ⚠️ 实体/关系 | ✅ 聚合/实体/值对象 | ✅ DDD完整概念 |
| **DSL支持** | ❌ 无 | ✅ CML语言 | ✅ JDL语言 | ✅ 自研DSL | ❌ |
| **关系可视化** | ❌ 无 | ✅ 上下文映射图 | ✅ 实体关系图 | ✅ 类图 | ❌ |
| **逆向工程** | ❌ 无 | ✅ Java代码→上下文映射 | ❌ | ❌ | ✅ 代码→模型 |
| **导入导出** | ❌ 无 | ✅ PlantUML/JSON/MDSL | ✅ JDL导入导出 | ✅ PNG/SVG | ❌ |
| **版本管理** | ❌ 无 | ❌ | ❌ | ❌ | ❌ |
| **事件建模** | ⚠️ 事件流水跟踪 | ✅ 领域事件建模 | ❌ | ✅ 事件风暴 | ✅ 领域事件 |
| **权限管理** | ✅ 基础RBAC | ❌ | ✅ JHipster权限 | ❌ | ❌ |

### 1.3 核心差距分析

通过对比分析，Z-Model当前存在以下**五个核心差距**：

#### 差距1：缺乏可视化建模能力（严重）
- 当前：纯表单CRUD操作，无任何图形化建模
- 业界标准：拖拽建模（SketchDDD）、UML类图（JDL Studio）、ER图（ERDPlus）
- 影响：用户无法直观理解模型结构，建模效率低

#### 差距2：缺乏代码生成能力（严重）
- 当前：仅做模型数据管理，无代码输出
- 业界标准：从模型生成JPA实体、Controller、前端页面（JHipster）
- 影响：模型无法直接驱动开发，业务价值受限

#### 差距3：DDD核心概念缺失（中等）
- 当前：Model/Property/Method/Event，无DDD概念
- 业界标准：限界上下文（Bounded Context）、聚合（Aggregate）、值对象（Value Object）、领域事件（Domain Event）
- 影响：无法支撑复杂业务的DDD落地

#### 差距4：缺乏模型导入导出能力（中等）
- 当前：无导入导出功能
- 业界标准：PlantUML、JDL、JSON、DDL脚本导出
- 影响：模型无法与其他工具链集成

#### 差距5：缺乏模型关系可视化（中等）
- 当前：需求-模型-属性-方法的关系仅在详情页以列表展示
- 业界标准：关系图自动布局、交互式导航
- 影响：模型间关系不直观，追溯困难

## 二、改进结论

**明确结论：需要改进。**

Z-Model作为一个需求驱动的模型管理系统，在需求追溯和关联管理方面有独特优势，但在**可视化建模、代码生成、DDD概念支持**三个核心维度上与业界领先平台存在明显差距。

改进的核心目标：
1. **从"模型注册表"升级为"模型驱动开发平台"**
2. **让模型可被开发工具链消费（代码生成、可视化）**
3. **丰富DDD建模概念，支撑复杂业务场景**

## 三、改进计划（分阶段实施）

### 第一阶段：可视化建模与关系可视化（优先级：最高）

**目标**：为现有模型增加可视化展示能力，让用户能直观看到模型结构和关系

#### 3.1.1 UML类图可视化
- **功能**：在模型详情页增加UML类图Tab，展示模型的属性和方法
- **技术方案**：
  - 使用 **Mermaid.js** 或 **PlantUML.js** 进行前端渲染
  - 后端新增 `/api/models/{id}/diagram` 接口，根据模型数据生成PlantUML/Mermaid文本
  - 支持导出PNG/SVG图片
- **涉及模块**：
  - 后端：新增 `DiagramController`、`DiagramService`
  - 前端：新增 `ModelDiagram.vue` 组件（集成在ModelDetail中）

#### 3.1.2 ER关系图可视化
- **功能**：展示所有模型之间的关系图，包括需求关联
- **技术方案**：
  - 使用 **AntV G6** 或 **GoJS** 实现关系图
  - 节点：需求、模型、属性、方法
  - 连线：关联关系（需求→模型→属性/方法）
  - 支持交互：点击节点跳转详情、缩放拖拽
- **涉及模块**：
  - 后端：新增 `/api/relationships/graph` 接口
  - 前端：新增 `GraphView.vue` 页面

#### 3.1.3 仪表盘增强
- **功能**：在仪表盘增加模型关系概览图
- **涉及模块**：修改 `Dashboard.vue`

---

### 第二阶段：代码生成引擎（优先级：高）

**目标**：从模型自动生成可运行的代码骨架，实现"模型驱动开发"

#### 3.2.1 Java/JPA实体生成
- **功能**：根据Model+Property自动生成JPA实体类
- **生成内容**：
  - 实体类（@Entity注解）
  - Repository接口
  - DTO（请求/响应）
  - Service层
  - Controller层
- **技术方案**：
  - 使用 **FreeMarker** 模板引擎
  - 定义代码模板：entity.ftl, repository.ftl, dto.ftl, service.ftl, controller.ftl
  - 后端新增 `/api/generate/java` 接口，返回zip包
- **涉及模块**：
  - 后端：新增 `codegen` 包，包含模板引擎和模板文件
  - 前端：新增代码生成对话框（在ModelDetail页）

#### 3.2.2 SQL DDL生成
- **功能**：根据模型生成MySQL建表语句
- **技术方案**：
  - 根据Property的dataType映射到MySQL类型
  - 生成CREATE TABLE语句，包含外键、索引
- **涉及模块**：与3.2.1共用生成引擎

#### 3.2.3 前端页面代码生成
- **功能**：根据模型自动生成Vue3+Element Plus的CRUD页面
- **生成内容**：
  - List页面（表格+搜索）
  - Form页面（表单验证）
  - API调用文件
- **涉及模块**：与3.2.1共用生成引擎

---

### 第三阶段：DDD概念 enrichment（优先级：中）

**目标**：引入DDD核心概念，支撑更复杂的业务建模

#### 3.3.1 限界上下文（Bounded Context）
- **功能**：新增限界上下文实体，用于定义业务边界
- **数据库设计**：
  - `bounded_context` 表：id, name, code, description, status
  - `bounded_context_model` 关联表：context_id, model_id
- **API设计**：
  - CRUD接口：/api/bounded-contexts
  - 关联管理：/api/bounded-contexts/{id}/models
- **前端页面**：
  - 限界上下文列表页
  - 上下文详情页（展示关联的模型和关系图）

#### 3.3.2 聚合（Aggregate）
- **功能**：在模型之上引入聚合概念，定义聚合根
- **设计**：
  - Model增加 `aggregate_root` 标记字段
  - 新增 `value_object` 实体，与Model关联
  - 支持聚合内模型的一致性边界定义

#### 3.3.3 领域事件（Domain Event）
- **功能**：将当前Event模块升级为DDD领域事件建模
- **设计**：
  - 新增 `domain_event` 表：id, name, code, description, trigger_condition
  - 支持事件与模型/方法的关联
  - 支持事件触发规则定义
- **前端**：领域事件建模页面，支持事件溯源图

#### 3.3.4 值对象（Value Object）
- **功能**：支持值对象的定义，增强模型表达力
- **设计**：
  - 新增 `value_object` 表：id, name, model_id, attributes（JSON存储内嵌属性）
  - 值对象作为模型的组成部分

---

### 第四阶段：导入导出与集成（优先级：中）

**目标**：让Z-Model能与其他建模工具链无缝集成

#### 3.4.1 模型导出
- **导出格式**：
  - **PlantUML**：导出UML类图、ER图的PlantUML源代码
  - **JSON**：导出完整模型定义（含所有关联）
  - **JDL**：导出JHipster兼容的JDL格式
  - **DDL**：导出MySQL建表语句
  - **Markdown**：导出模型文档
- **涉及模块**：后端 `export` 包，前端导出按钮

#### 3.4.2 模型导入
- **导入格式**：
  - **JDL导入**：解析JHipster的JDL文件，导入实体和关系
  - **DDL导入**：解析MySQL DDL，生成属性定义
  - **JSON导入**：从Z-Model导出的JSON恢复
- **涉及模块**：后端 `import` 包

#### 3.4.3 数据库逆向工程
- **功能**：连接已有数据库，自动生成模型定义
- **技术方案**：
  - 使用JDBC元数据读取表结构
  - 生成Property定义（字段名→属性名，类型→dataType）
  - 生成关系定义（外键→模型关联）
- **涉及模块**：后端新增 `reverse` 包

---

### 第五阶段：协作与版本管理（优先级：低）

**目标**：支持团队协作和模型版本管理

#### 3.5.1 模型版本管理
- **功能**：自动记录模型变更历史，支持版本对比和回滚
- **设计**：
  - 新增 `model_version` 表：记录每次变更的快照
  - 支持版本差异对比（diff）
  - 支持回滚到历史版本
- **涉及模块**：后端 `version` 包

#### 3.5.2 多租户与协作
- **功能**：支持多团队/多项目隔离
- **设计**：
  - 新增 `tenant` 概念
  - 数据隔离（按tenant_id）
  - 权限增强（项目级、模型级权限）

#### 3.5.3 模型模板
- **功能**：提供常用业务场景的模型模板
- **模板示例**：
  - 订单模型模板
  - 用户权限模型模板
  - 支付模型模板
- **涉及模块**：后端 `template` 包

## 四、技术选型建议

| 需求 | 推荐方案 | 备选方案 | 说明 |
|------|---------|---------|------|
| UML类图渲染 | Mermaid.js | PlantUML.js | Mermaid语法更简洁，PlantUML更专业 |
| ER图渲染 | AntV G6 | GoJS / vis.js | G6开源免费，功能强大 |
| 代码模板引擎 | FreeMarker | Thymeleaf | FreeMarker更通用，适合代码生成 |
| 数据库连接池 | HikariCP | - | Spring Boot默认，性能最优 |
| 导出ZIP | java.util.zip | Apache Commons Compress | JDK内置即可 |

## 五、实施优先级与依赖关系

```
第一阶段（可视化） ──────→ 第二阶段（代码生成） ──────→ 第三阶段（DDD概念）
                                                            │
                                                            ▼
                                          第四阶段（导入导出） ──→ 第五阶段（版本协作）
```

**建议实施顺序**：
1. **第一阶段**（可视化建模）：快速提升用户体验，展示系统价值
2. **第二阶段**（代码生成）：实现核心业务价值，模型直接驱动开发
3. **第三阶段**（DDD概念）：扩展建模能力，支撑复杂场景
4. **第四阶段**（导入导出）：增强生态集成能力
5. **第五阶段**（版本协作）：完善团队协作支持

## 六、风险与注意事项

1. **渐进式改造**：每个阶段独立实施，避免大爆炸式重构
2. **数据兼容**：新增DDD概念时，确保现有数据平滑迁移
3. **模板定制**：代码生成模板需充分调研团队编码规范
4. **性能考虑**：关系图可视化需考虑大规模模型的渲染性能（如虚拟化渲染）
5. **安全考量**：代码生成和逆向工程涉及文件系统访问，需注意安全
